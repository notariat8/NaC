## Goal and boundary

A new, separately approved future Teams test should use one protected
internal BFF event to identify the coarse branch that caused the workbench
403. Existing client receipts prove an available SPFx subject and HTTP 403,
not the BFF or authorization cause. The public response remains unchanged.
The historical [request-log triage contract](../../../../workflows/verification-contracts/m365-bff-request-log-triage.verification.json)
remains `OFFLINE_ONLY_NOT_LIVE_CAPABLE`; #739 and #632 stay blocked.

## Test-first implementation after plan approval

1. **Define tests before code (AC-748-BD-01, -02).** Add synthetic cases in
   `tests/test_nac_bff_403_diagnostic_event.py` for scope rejection,
   access-decision port failure, invalid or denied decision, and a 403 before
   the domain endpoint. They expect only `REQUEST_SCOPE_REJECTED`,
   `ACCESS_DECISION_UNAVAILABLE`, `ACCESS_DECISION_REJECTED` or
   `DENIAL_UNCLASSIFIED`. Compare exact public 403 body bytes
   `{"status":403,"error":{"code":"ACCESS_DENIED"}}`, status and security
   headers with existing fixtures. Denial or failure inside the live
   access-decision adapter remains in the coarse
   `ACCESS_DECISION_REJECTED` class.
2. **Test correlation and privacy negative paths first (AC-748-BD-03, -04).**
   Tests prove at most one event per eligible request and treat an inactive
   sink, sink exceptions and missing telemetry as missing evidence without
   changing access or response. Only exactly one received
   `X-Correlation-ID` header carrying a `spfx-` UUID-v4 generated by one
   `crypto.randomUUID()` call may be hashed in memory before any fallback.
   Positive matching also requires the same SHA-256 binding in a new
   protected client receipt; syntax alone is insufficient. Missing,
   duplicate, combined, rewritten or mismatching headers and unproven
   receipt binding remain `UNBOUND`.
   A missing or invalid single header yields no correlatable event and no
   replacement hash; an event for a syntactically valid single header may
   carry only the hash of that received value. Only a later protected receipt
   comparison may associate the event with a client attempt. Negative
   fixtures forbid raw headers,
   URL/path/query, claims, IDs, names, roles, grants, Graph data, tokens and
   exception text in the event and public logs.
3. **Implement the closed internal path (AC-748-BD-01 through -04).** Only
   for the fixed workbench-snapshot GET of synthetic `notary_team_01`,
   determine the reason at the existing decision points in
   [workbench_endpoint.py](../../../../src/nac_bff/workbench_endpoint.py).
   Transfer it only through request-local, non-serialized state to the
   once-invoked sink at the [FastAPI boundary](../../../../src/nac_bff/fastapi_adapter.py);
   a 403 before the endpoint is `DENIAL_UNCLASSIFIED`. The sink remains
   inactive by default and accepts only schema version, bounded UTC time,
   constant `workbench_snapshot` route class, `GET` method, `403` HTTP
   class, closed reason class and
   `request_correlation_binding_sha256`. No free-text or metadata field, new
   mandatory SDK or change to access-decision/provider semantics. Treat
   sink failure as missing evidence; it must not grant access or alter the
   response or provider call.
4. **Forward contract and fail-closed gates (AC-748-BD-05, -06).** Create a
   separate forward-versioned contract at
   `workflows/verification-contracts/m365-bff-403-diagnostic-event.verification.json`,
   `scripts/validate_m365_bff_403_diagnostic_event.py` and synthetic
   negative tests. Keep `provider_read_authorized=false` and
   `deployment_authorized=false` until separate target, package/commit/tree,
   DPA/AVV, retention, access, telemetry, client-receipt and owner bindings
   are established; do not reconstruct historical evidence. Leave the
   existing triage contract unchanged. Accounts of one principal must never
   act as independent approvers. Without a concretely cited applicable
   external two-person requirement, documented `OWNER_SOLO_APPROVAL` with
   `four_eyes_satisfied=false` is permitted; if that requirement calls for
   two natural principals and only one is available, use
   `BLOCKED_SINGLE_PRINCIPAL`. A claimed requirement without a source/scope
   binding yields `BLOCKED_REQUIREMENT_CITATION_MISSING`. Negative tests and
   the contract must enforce these boundaries.
5. **Synchronize and review (AC-748-BD-06).** DE/EN specification and plan,
   traceability, contract, validator and tests carry the same six ACs.
   Documentation describes the inactive state and the limited meaning of
   `ACCESS_DECISION_REJECTED`. No new `nac` CLI surface arises from an
   internal-only event; specify any later operator action separately before
   implementing it. Change SBOM/AI-SBOM only for an actual new runtime or
   AI component. Run `implement -> review -> fix` with independent privacy,
   security and DE/EN review.

## Validation gates and completion boundary

After separate plan and implementation approval: focused negative tests and
existing workbench/host tests, validator, spec traceability, DE/EN parity,
documentation links, privacy/secret gates, `graft build`, `graft check` and
`python scripts/nac.py doctor --profile strict`. Before any later publication,
   review the full `main...HEAD` file and commit lists, push only the bound scope
   and evaluate required remote CI. Push or PR mutation requires a separate,
   scope-bound approval; plan approval alone does not suffice. These are
   planned gates, not claims of
successful validation. Activation, Microsoft/provider read, new
reproduction, deployment, #739 release and #632 live run each require
separate, exactly bound approvals. A future `ACCESS_DECISION_REJECTED` alone
does not prove a specific Graph or role defect or a fix.
